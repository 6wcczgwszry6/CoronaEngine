## 1. 当前目标、约束与事实起点

### 1.1 本周目标

在低美术质量可接受的前提下，形成一条约 40-50 秒可玩的单人垂直链：

```text
用户提出 Demo 目标
-> 策划 Agent：GameDesignBrief + LevelPlan
-> 美术 Agent：ArtDirection + SceneCompositionPlan
-> 程序 Agent：GameplayLogicPlan
-> 房主确认
-> AgentRuntime 场景生成
-> SceneWorldSnapshot
-> EntityBindingPlan
-> 白名单玩法原语
-> 单人预览与完成目标
```

固定玩法：

```text
玩家出生
-> 走到桌边拾取钥匙
-> 使用钥匙解锁门
-> 进入终点区域
-> 完成目标并显示成功
```

### 1.2 当前事实

- 完整 R3 Gate 仍为 `red / pending_reevaluation`。
- 最新 Runtime / Native scene route / Finalizer 修复尚未经过新一轮 F5。
- 近几天无法稳定进行 F5，Engine 与 Frontend 的 `main` 分支仍在发生较大变化。
- 三职能 Track B 独立聚焦测试 81 项通过。
- R3 readiness 独立聚焦测试 21 项通过。
- 两组测试在同一 Python 进程运行时存在 3 项隔离测试误报，原因是测试读取被其他测试污染的 `sys.modules`。
- `ArtifactEnvelope`、content hash、真实 Validator、Mock 隔离和 `assert_executable()` 已存在。
- `RuntimeCppBridge`、Engine providers、C++ Editor API manifest 和 Frontend Bridge 已存在。
- 本周不重新实现上述能力，只冻结接口、补足隔离层和完成单人垂直闭环。

### 1.3 本周状态口径

只允许使用以下完成口径：

```text
code_complete
  代码与聚焦自动测试完成，尚无集成或实机证据

integration_ready
  契约、Adapter、Test Double、Runner 和迁移清单完整，等待稳定底层 SHA

single_player_verified
  在稳定 Engine SHA 上通过最小 F5 和两次独立单人 Demo Session

full_r3_verified
  仍按完整 R3 文档执行，本周不默认宣称完成
```

`integration_ready` 不等于 Engine-ready、Game-ready 或完整 R3 Green。

## 2. 架构不变量与责任边界

### 2.1 现有 Runtime 主链保持不变

```text
ScenePlan -> BatchPlan -> ToolCallGraph
-> RuntimeGuard -> EngineWriteGate / RuntimeCppBridge
-> ToolResult -> StatePatch
-> RuntimeState -> OperationLog
-> Registry -> SceneWorldSnapshot
```

硬约束：

1. Agent、Coordinator 和 ProjectGate 不直接写 Engine。
2. 不新增可供上层直接调用的公共 `EngineAdapter.create_actor()`。
3. Engine 写入继续使用已有 `RuntimeCppBridge`，并且只能在 EngineWriteGate 后执行。
4. Frontend 不承载项目状态、Gate 结论或执行事实判断。
5. Mock / fixture 可以用于测试，但不能构造可执行 ActionProposal。
6. Engine 返回事实优先于 Agent、计划、名称和估算结果。
7. EntityBindingPlan 只能引用指定 Snapshot 版本中的稳定 `entity_id`。
8. 不恢复 SceneComposer / ProgressiveWorkflow 为用户主入口。

### 2.2 三方责任

```text
AI / Runtime 组
  领域契约、Python 端口、Test Double、Gate profile、Demo Runner、证据包

Engine 组
  Native method/event manifest、白名单玩法原语、稳定 24 小时集成 SHA

Frontend 组
  UserCommand / ProgressEvent 映射、确认与进度展示、预览入口

集成 owner
  锁定 SHA、维护兼容差异表、组织第 6-7 天 F5 和结果归档
```

Adapter 采用共同契约、分层维护，不由单一团队跨层修改全部实现。

### 2.3 框架先行：Walking Skeleton

本周不采用“完整写完一个模块，再开始下一个模块”的纵深顺序。先建立一条可运行、可阻断、可观测的端到端骨架，再沿骨架填充各层细节：

```text
UserCommand fixture
-> Demo Scenario Runner
-> Planning / Art / Program Agent
-> Artifact bundle
-> ProjectGatePreflight
-> EngineCapabilityPort
-> DemoResult(status=pending_runtime_verification)
-> ProgressEvent fixture
```

Walking Skeleton 必须满足：

- 数据结构、依赖方向、调用入口和错误传播真实存在。
- 每层只有最小确定性实现，不提前扩展完整业务功能。
- 未实现的 Engine / Frontend 能力返回 `unavailable`、`blocked` 或 `pending_runtime_verification`。
- 禁止 `pass`、空字典、固定“成功”或 Mock Green 作为临时实现。
- 骨架不创建 ActionProposal、PlanPatch、ToolCallGraph 或 Engine 写入。
- 骨架通过后，B1-B5 只能沿既有端口补细节，不再引入第二套主链。

框架先行不是大而全设计。每个骨架接口必须服务本周固定 Demo，并通过一项端到端契约测试；不为未来战斗、剧情、蓝图或多人能力预建空壳。

### 2.4 架构 AI 与填充 AI 串行交接

本周采用串行交接，不允许两个角色并发修改骨架：

```text
架构 AI
-> 完成 B0.1-B0.4
-> 冻结接口、节点 ID、数据流和 skeleton contract hash
-> 输出 SkeletonStatusReport

填充 AI
-> 从优先级最高且依赖满足的 blocked 节点开始
-> 每轮只填充一个节点
-> 不修改已冻结公共接口
```

架构 AI 不只创建接口签名，还必须完成最小编排、统一阻断诊断和端到端骨架测试。填充 AI 如发现接口不足，必须提交 `InterfaceChangeRequest` 并停止，不得自行改变签名或建立旁路；只有架构 AI 可以作出 `InterfaceChangeDecision`。

## 3. 隔离架构与公共契约

### 3.1 Engine 隔离层

生产实现继续复用 `services/agent_runtime/adapters.py`。新增的稳定端口仅覆盖能力发现和只读事实：

```python
class EngineCapabilityPort(Protocol):
    def get_manifest(self) -> EngineCapabilityManifest: ...

class EngineSnapshotPort(Protocol):
    def get_snapshot(self, request: SceneSnapshotRequest) -> SceneWorldSnapshot: ...
```

写入边界继续使用：

```python
RuntimeCppBridge.invoke_tool(...)
```

不得让 `services/agent_collaboration/` import Engine port、RuntimeCppBridge、C++ DTO 或 SceneTools。

`EngineCapabilityManifest`：

```text
contract_version
bridge_version
snapshot_schema_version
supported_operations
supported_gameplay_primitives
```

单人 Demo 所需操作：

```text
actor_create
scene_snapshot
actual_aabb
render_ready
gameplay.apply_manifest
gameplay.preview.start
```

单人 Demo 所需玩法原语：

```text
on_enter
on_collect
set_state
unlock
complete_objective
```

若任一必要能力缺失，ProjectGate 必须返回 `engine_capability_missing`，不得回退任意脚本。

### 3.2 Frontend 隔离层

复用 `editor/Frontend/src/utils/bridge.js` 的 C++ manifest 通讯能力，只增加业务命令和事件映射层。

`UserCommand`：

```text
schema_version
command_id
room_id
command_type:
  start_project | confirm_action | query_status | start_preview
payload
```

`ProgressEvent`：

```text
schema_version
event_id
command_id
room_id
project_id
task_id
plan_id
scene_version
event_type
status
detail
```

约束：

- 相同 `command_id` 只能产生一次权威业务动作。
- 相同 `event_id` 在 Frontend store 中只能消费一次。
- AI 页面不得直接调用 `sceneTools.createActor`、`removeActor` 或其他场景写 API。
- Frontend 只展示结构化进度，不根据聊天文本推断完成状态。

### 3.3 分域版本

Python 侧版本统一放在 `editor/plugins/AITool/services/schema_versions.py`，禁止各模块重复声明：

```text
COLLABORATION_SCHEMA_VERSION = "1.1"
SCENE_WORLD_SNAPSHOT_SCHEMA_VERSION = "r3-scene-world-v1"
R3_GATE_SCHEMA_VERSION = "r3-gate-v1"
ENGINE_ADAPTER_CONTRACT_VERSION = "r3-engine-week1-v1"
FRONTEND_INTERACTION_SCHEMA_VERSION = "r3-interaction-week1-v1"
SKELETON_CONTRACT_VERSION = "r3-skeleton-week1-v1"
```

版本规则：

- Runtime、协作层和 Python Adapter 只能从 `schema_versions.py` import 版本。
- Engine / Frontend 的自身版本由各自 manifest 返回，Python Adapter 与集中登记版本做兼容检查。
- 第 2 天后发生破坏性变更必须提升对应 domain version。
- 历史 Snapshot / Artifact 可读取和审计，但标为 legacy 或 stale。
- legacy Snapshot 不得进入 ProjectGate 的可执行路径。
- schema version 必须参与 Artifact content hash、Snapshot fingerprint 或 Gate evidence。

### 3.4 统一阻断诊断

所有骨架节点使用同一个无 Runtime、Frontend、C++ 依赖的结果契约：

```python
@dataclass(frozen=True)
class MissingRequirement:
    requirement_id: str
    owner_domain: str
    description: str

@dataclass(frozen=True)
class BlockedResult:
    node_id: str
    status: str  # unavailable | blocked | pending_runtime_verification
    error_code: str
    summary: str
    missing_requirements: tuple[MissingRequirement, ...]
    owner_domain: str
    retryable: bool
    next_action: str
    evidence_refs: tuple[str, ...]
```

`owner_domain` 只允许：

```text
ai_runtime | engine | frontend | collaboration | integration
```

约束：

- `error_code`、`owner_domain` 和 `next_action` 必填。
- `requirement_id` 必须匹配 `^[a-z][a-z0-9_.-]{2,63}$`，例如 `engine.gameplay_apply_manifest`；禁止使用自然语言句子作为 ID。
- `MissingRequirement.owner_domain` 必须属于允许的责任域。
- `unavailable/blocked/pending_runtime_verification` 均至少包含一个 MissingRequirement。
- 诊断不得包含密钥、签名 URL、原始 Provider 响应或异常堆栈。
- 未实现节点不得返回 `{}`、`True`、`None` 或固定 success。

骨架同时输出：

```text
SkeletonNodeStatus:
  node_id / interface_name / status
  blocker_code / owner_domain / fill_priority / evidence_refs

SkeletonStatusReport:
  contract_version / contract_hash
  nodes / overall_status / generated_at
```

### 3.5 Skeleton contract hash

contract hash 不对 `SkeletonStatusReport`、原始源码文件字节或自然语言说明做 hash。架构 AI 必须先生成规范化 `SkeletonContractManifest`：

```text
schema_versions
public_protocols:
  protocol name
  ordered method signatures
  parameter names/types/defaults
  return types
public_dtos:
  DTO name
  ordered field names/types/defaults
public_enums:
  enum name / ordered values
skeleton_nodes:
  node ID / interface name / ordered edges
```

Manifest 使用 canonical JSON 序列化，再计算：

```text
sha256(canonical_json(SkeletonContractManifest))
```

规则：

- 接口签名、DTO 字段、枚举、schema version、节点 ID 或边顺序变化必须改变 hash。
- 注释、空白、格式化和私有实现变化不得改变 hash。
- SkeletonStatusReport 只引用 contract hash，不参与 hash 计算。
- 填充 AI 开始任务前必须校验当前 hash 与交接 hash 一致。

### 3.6 接口变更交接契约

填充 AI 发现冻结接口不足时提交：

```text
InterfaceChangeRequest:
  request_id
  node_id
  detected_by_task_id
  current_contract_version
  current_contract_hash
  reason_code
  required_change
  affected_interfaces
  blocked_dependents
  evidence_refs
```

处理顺序固定为：

```text
填充 AI 停止节点实现
-> 节点状态改为 blocked/interface_change_required
-> 写入 InterfaceChangeRequest
-> 架构 AI 判断是否可由私有实现解决
-> 输出 InterfaceChangeDecision
```

`InterfaceChangeDecision`：

```text
decision: accepted | rejected | no_contract_change
reason
changed_interfaces
new_contract_version
new_contract_hash
affected_nodes
required_revalidation
evidence_refs
```

若接受公共接口变更：

- 提升 `SKELETON_CONTRACT_VERSION`。
- 更新 Manifest 并重新计算 hash。
- 重跑 B0.4 全部骨架和架构依赖测试。
- 使用旧 hash 的下游节点标记 `stale/revalidation_required`。
- 形成新的架构 AI 交接包后，填充 AI 才能恢复。

## 6. 单人 Demo Gate Profile

### 6.1 与完整 R3 的关系

`runtime.r3_readiness.evaluate` 支持：

```text
profile=full_r3
profile=single_player_demo
```

默认继续使用 `full_r3`。单人 profile 不覆盖或修改完整 R3 的结果。

### 6.2 动态要求来源

Runtime 层不得读取 GameplayLogicPlan。

ProjectGate 从已经验证的 `GameplayEntitySlot` 派生：

```text
DemoReadinessRequirement:
  requirement_id
  semantic_role
  required_capabilities
  min_count
```

Runtime evaluator 只检查这些结构化要求，不理解 Artifact 语义。GateReport 必须记录 requirements fingerprint 和匹配到的 entity IDs。

不得在 Gate 代码中硬编码 `player_spawn`、`collectible_key`、`locked_door` 或 `goal_zone`。

### 6.3 单人 Green 条件

必须全部满足：

- 必要环境实体 ready。
- Snapshot immutable 且 fingerprint 一致。
- Registry、Consistency Audit、Snapshot、Report 终态完整。
- 业务 Batch 与 business ToolGraph 数量和终态一致。
- RuntimeGuard 与 EngineWriteGate 边界有效。
- 每个动态 DemoReadinessRequirement 都有足量 Game-ready entity 匹配。
- 匹配实体满足 slot 声明的 capability。
- `project_mode=single_player` 且 peer count 为 0。
- 不存在 entity ID、asset ID 或 scene version 矛盾。

单人 profile 只解锁：

```text
single_player_entity_binding
single_player_local_action
single_player_preview
```

不解锁 multiplayer capability。

### 6.4 GameplayManifest


## 8. B0：基线与契约冻结

### B0.1 基准 SHA 与改动清单

- 目标：建立黑盒开发期间的比较基准和无已知噪声的测试门禁。
- 输入：当前 AI 分支 SHA、Engine main SHA、Frontend main SHA、工作区状态。
- 实施：记录三方 SHA 和 API manifest；修复 3 项依赖全局 `sys.modules` 的隔离测试误报；黑盒期每日只生成差异报告，不自动合并 main。
- 交付物：基准清单、Adapter 影响表、集成 owner、干净的 Track B + R3 合并门禁。
- 完成：能够指出任一底层变化只影响哪个 Adapter 契约；81 项 Track B 与 21 项 R3 测试在同一执行中通过。
- 不做：清理用户未提交改动或频繁 rebase。

### B0.2 集中 schema version 登记

- 前置：B0.1。
- 目标：冻结六个 domain version，消除散落版本字符串。
- 实施：新增纯常量 `schema_versions.py`；Runtime、协作层和 Python Adapter 改为统一 import。
- 完成：序列化结果携带正确版本；legacy 输入可识别但不可执行；源码检查不存在重复版本声明。
- 不做：要求 C++ 或 JavaScript import Python 文件；外部版本通过 manifest 对账。

### B0.3 BlockedResult 与节点清单契约

- 前置：B0.2。
- 目标：让所有未实现节点可诊断、可归责、可排序。
- 实施：定义 MissingRequirement、BlockedResult、SkeletonNodeStatus、SkeletonStatusReport、SkeletonContractManifest、InterfaceChangeRequest/Decision 和 Validator。
- 完成：缺失诊断字段无法构造；相同节点事实产生相同状态表和 contract hash。
- 不做：把底层异常原文或敏感 Provider 信息写入诊断。

## 18. 失败处理与阻断规则

- 第 2 天无法冻结契约：暂停依赖该契约的 Adapter 实现，先完成 fixture 和字段决策。
- 第 5 天缺少 `gameplay.apply_manifest` 或任一 primitive：Demo 标记 blocked，不回退脚本。
- 第 6 天没有稳定 Engine SHA：本周最高状态为 `integration_ready`。
- capability manifest 与实现不一致：由对应底层 owner 修正，AI 层不猜测。
- 最小 F5 失败：只修 Adapter、Engine observation、Snapshot 或 Finalizer 断点。
- Frontend 未稳定：使用 Demo Runner 完成后端集成证据，不阻塞后端 `integration_ready`。
- RuntimeGuard 绕过、Snapshot identity 漂移、Mock 可执行或用户改动冲突：立即停止并记录 blocker。
- 同一技术假设连续失败两次：停止继续补丁，重新诊断接口和事实来源。
- 节点需要 F5 后，只允许继续与该真实 Engine 结果无依赖的节点；消费该结果的下游节点保持 blocked。
- 填充 AI 发现公共接口不足时提交 InterfaceChangeRequest，交回架构 AI，不得自行改签名。

## 20. AI 续跑协议

后续 AI 每轮必须执行：

```text
读取本计划与 R3-min推进记录
-> 读取最新 GateReport / integration status
-> 确认当前 B 工作块和任务编号
-> CodeGraph 核实现有实现与依赖
-> 只选择一个最早 ready 的任务
-> 最小实现
-> 按验证预算测试
-> 回写证据、状态和下一任务
```

角色阶段固定为：

```text
架构 AI 阶段：B0.1 -> B0.2 -> B0.3 -> B0.4
串行交接门：合并门禁通过 + skeleton 测试通过 + ContractManifest/hash + 节点状态表
填充 AI 阶段：从状态表选择最高优先级且依赖满足的 blocked 节点
```

填充 AI 每轮开始必须校验交接 hash 并读取该节点的 BlockedResult；每轮结束必须更新对应 SkeletonNodeStatus。没有满足依赖的节点不得因为“可以写代码”而标记 ready。若提交 InterfaceChangeRequest，则必须等待架构 AI 的 InterfaceChangeDecision。

确定性选题顺序：

```text
B0 未完成 -> B0
B0.1 干净合并门禁 -> B0.2 schema version
B0.2 完成 -> B0.3 统一阻断诊断
B0.3 完成 -> B0.4 Walking Skeleton
B0.4 完成且黑盒 -> B1/B2 与 B3/B4 的最早 ready 任务
B1-B4 完成 -> B5
B5 integration_ready 且无稳定 SHA -> 维护 fixture/差异报告，不扩功能
稳定 SHA 到达 -> B6
最小 F5 条件满足 -> B7.1
B7.1 通过 -> B7.2
```

每轮最终只报告：

```text
完成的任务编号
修改范围
验证证据
当前 integration / Gate 状态
[待 F5/实机验证] 项
Skeleton contract version/hash
当前节点及 BlockedResult
下一个 ready 任务
```

禁止行为：

- 因为无法 F5 就把 Test Double 结果写成 verified。
- 在 `lanchat_agent_worker.py` 或 `agent_runtime/core.py` 继续堆积三职能业务逻辑。
- 重复实现已有 Artifact、R3GateReport、RuntimeCppBridge 或 Frontend transport Bridge。
- 为保持忙碌新增计划外 Agent、测试矩阵、UI 或 Provider。
- 在没有新证据时修改 Gate 结果或完成声明。
