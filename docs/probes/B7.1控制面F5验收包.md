# B7.1 控制面 F5 验收包

状态：`ready_for_f5`，所有结果在执行前均为 `[待F5/实机验证]`。

## 1. 执行前提

- 使用全新单人 Session，不复用旧 room、history 或 RuntimeState。
- 记录本次 AI/Engine/Frontend SHA 与工作区 patch fingerprint。
- 确认模型连接可用；连接失败时本轮只记环境阻断，不判控制面通过。
- 不同时执行森林、混合场景、多人或完整玩法 Demo。

## 2. 固定五个业务回合 + 一个问候探针

严格按顺序逐条发送，上一条 final reply 到达后再发送下一条：

```text
@小女孩 围绕迪士尼乐园主题讨论一下
@小女孩 按照迪士尼风格的卧室来设计呢
@GM 确认生成
@长者 请你给出一个方案
@长者 确认开始
@小女孩 你好
```

不得临时改写文本，否则 probe 会判定固定场景覆盖失败。最后一条只验证回复相关性，不计入业务方案回合，也不得重新激活已完成计划。

## 3. 自动验收命令

```powershell
python docs/probes/r3_f5_log_check.py `
  --profile control-plane `
  --history <本次LANChat history.jsonl> `
  <本次_corona.log>
```

需要机器可读证据时增加 `--json`。

## 4. 通过标准

最终摘要必须为：

```text
B7_1_CONTROL_READY
```

并同时满足：

- 五个业务回合和一个问候探针各出现一次。
- 每轮恰好一个 processing owner、一次权威执行和一条 final reply。
- 讨论/问候由显式 persona 回复；正式方案、协作状态、协作失败和 Red Gate 确认阻断由 GM 回复。
- 每轮都有 `LANChatModelCallSummary`；讨论/问候恰好一次 `agent_visible_reasoning`；每个方案依次且仅调用 `planning_artifact_reasoning -> program_artifact_reasoning -> art_artifact_reasoning -> collaboration_proposal_narration`；确认消息为 0 次。
- 每次方案的四个 `LANChatModelCallResult` 均存在，单阶段不超过 90 秒，四阶段累计不超过 180 秒。
- 方案和对应确认携带完全相同的 `proposal_id/proposal_version/proposal_hash/artifact_refs`。
- Full R3 Red 时确认回复契约为 `runtime_write_blocked`，pending proposal 保留，零 ActionProposal、ToolGraph 和 Engine 写入。
- 问候回复包含针对性问候语，且不携带旧 `proposal_id/artifact_ref` 或方案模板。
- 无命令片段实体、重复 heartbeat、双 Quasar 根、乱码 sender、诊断倾倒或 Runtime/reply 矛盾。

任何 `FAIL` 均不得进入 B7.2。出现 `WARN` 时保留证据并人工确认来源，未消除前不标记 B7.1 verified。
