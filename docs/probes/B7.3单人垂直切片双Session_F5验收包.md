# B7.3 单人垂直切片双 Session F5 验收包

状态：`blocked_by_B7.1_B7.2_B6.4 / prepared`。所有玩法与实机结论均为 `[待F5/实机验证]`。

## 1. 执行人与预计耗时

- 执行人：Engine/AI/Frontend 集成人员；一人可操作，至少由另一人复核证据。
- 预计耗时：35-50 分钟。
- 前置：B7.1、B7.2 和 B6.4 写入回执全部通过。

## 2. 固定玩法

```text
玩家出生
-> 走到桌边拾取钥匙
-> 使用钥匙解锁门
-> 进入终点区域
-> complete_objective
-> 显示成功
```

只允许：`on_enter/on_collect/set_state/unlock/complete_objective`。不增加战斗、剧情分支、任意脚本、蓝图生成或多人同步。

## 3. Session A

1. 新建全新 room/project/plan/runtime state/registry。
2. 生成必要环境和动态 GameplayEntitySlot 实体。
3. 等待 Snapshot 冻结并运行 `single_player_demo` Gate。
4. 生成 EntityBindingPlan、GameplayManifest 和 ActionProposal。
5. 应用 Manifest，启动试玩并完成 40-50 秒流程。
6. 在同一 Session 内，使用相同 `command_id + payload_hash` 重放一次提交。

重放前后记录：

```text
PlanPatch count
business_action ToolGraph count
Engine gameplay receipt count
Actor count
Gameplay component/trigger count
Snapshot scene_version/fingerprint
```

这些计数在重放后不得增加。

## 4. Session B

彻底关闭并新建第二个独立 Session，重新创建 room/project/plan/runtime state/registry；不得复制 Session A 的 RuntimeState、Registry、Snapshot 或 receipt。

再次完成同一 40-50 秒流程。Session B 可以使用新的 ID，但其 Engine、RuntimeState、Registry、Snapshot、Artifact 和 Report 内部身份必须一致。

## 5. 每个 Session 的验收清单

- 必要环境实体 ready，所有被 EntityBindingPlan 引用的实体均 Game-ready。
- EntityBindingPlan 只引用目标 Snapshot 中存在的稳定 `entity_id + entity_version + asset_id`。
- GameplayManifest hash、Proposal、PlanPatch 和 Engine receipt 一一对应。
- 玩家只能在收集钥匙后解锁门；未收集钥匙时不得提前通过。
- 进入目标区域后只完成一次 objective，只显示一次成功状态。
- Actor、trigger、PlanPatch、业务图和 receipt 均无重复。
- RuntimeGuard 和 EngineWriteGate 没有绕过路径。
- Registry、Consistency Audit、Snapshot、Report 同版本，`report_ready` 最后发布。
- Full R3 Gate 保持诚实；单人 Demo 通过不等于多人或完整 R3 通过。
